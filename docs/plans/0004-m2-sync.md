# Plan 0004: M2 sync

M2 makes every device's notesd sync its vaults through a hub, a notesd in
the hub role, without losing an edit: devices push changed files with the
revision they last agreed on, only the hub merges, and a device applies
what it pulls only where nothing changed since. It follows
[M1](0003-m1-headless-vault.md), whose write path, versions and blob store
it builds on, and comes before M3's desktop app in the
[roadmap](0002-roadmap.md), because sync shapes storage and is the
riskiest part. Work is split per
[ADR-0010](../adr/0010-claude-plans-and-codex-runs-task-cards.md): the
planner owns the ADRs, the specs, the schemas and the migration, pairing
and the hub's token check, the hub's log and merges, the device's apply
path and sync loop, and the simulation's harness and checks; the executor
owns cards T-0024 onward.
Status (2026-10-25): **done.** Evidence 3, the 7-day trial on the user's
vault, ended on 2026-10-24, and the user accepted it on 2026-10-25
([Phase 7](#phase-7--review-and-exit-evidence)). The user accepted
Phase 1's ADRs as written on 2026-10-17. Done: this plan, ADRs

## Decisions taken for M2

Five decisions extend the architecture, so they are ADRs, written in
Phase 1 before any code:

- **Pairing and device tokens**
  ([ADR-0016](../adr/0016-pair-devices-with-a-one-time-code-and-a-revocable-token.md)).
  `notesctl hub join <url> <vault>` asks the hub to pair and shows a
  one-time code of 8 characters; the user approves it on the hub's
  machine, over its local socket (`notesctl hub approve <code>`), so no
  network caller can approve a device. The device then collects a random
  256-bit token, kept in the Secret Service; the hub keeps only its
  SHA-256. Every sync request carries the token, revoking a device closes
  its connections at once, and a device refuses a hub URL that is not
  `https://` unless it is loopback: TLS comes from a reverse proxy or
  `tailscale serve` until M4 decides on built-in TLS.
- **What a revision is**
  ([ADR-0017](../adr/0017-revisions-number-the-hubs-log-and-hashes-name-content.md)).
  M1's base is a content hash, and stays so for every local writer. A
  revision is an entry in a hub vault's log: a sequence number without
  gaps, the hub's file ID, the file's path, its content hash or deletion,
  its base revision, and who made it. The hash names content; the
  sequence number names a place in history, which a hash cannot (content
  can return to an earlier hash) and which pulls and cursors need. Devices
  push with a base revision and keep, per file, the agreed revision, path
  and hash. Every change to a served vault on the hub, a push, a local
  write or an outside edit, appends a revision in the same `Tx` as its
  local version, so the log and the hub's files agree after any crash.
  Revisions are about files: folders, `.frostnotes/` and ignored paths do
  not sync, which answers the roadmap's question on empty folders.
- **Blob transfer**
  ([ADR-0018](../adr/0018-move-blobs-over-http-named-by-their-hash.md)).
  Content moves outside JSON-RPC, over `PUT` and `GET /sync/blobs/<sha256>`,
  streamed and checked against its hash at both ends; a push names only
  hashes, after the device has uploaded those the hub lacks. JSON-RPC
  messages stop at 16 MiB and carry text
  ([ADR-0014](../adr/0014-the-api-carries-text-and-keeps-bytes-it-cannot-show.md)),
  and a 100 MB attachment must sync in bounded memory. Downloads resume
  with `Range`; uploads restart.
- **Hub retention**
  ([ADR-0019](../adr/0019-keep-every-revisions-record-and-thin-the-content-by-age.md)).
  The log's records are kept forever, so history and bases have no holes;
  content thins by age: every revision for 30 days, each file's last
  revision of each day for a year, then of each month; heads always, and
  conflict revisions while their file is flagged. A push whose base's
  content is gone merges as a create, with the lines both sides share as
  the base: nothing is lost, though lines may repeat. This answers the
  roadmap's question on retention.
- **The seeded simulation**
  ([ADR-0020](../adr/0020-test-sync-with-a-seeded-simulation-of-a-hub-and-devices.md)).
  `internal/synctest` runs a hub and devices as whole notesd instances in
  one process over loopback, with a seeded scheduler of edits, creates,
  moves, deletes, outside edits, offline periods, lost answers and
  crashes, and at each quiet point checks convergence, every token, the
  absence of conflict files and the log's invariants. Stepwise runs replay
  a seed exactly; concurrent runs find races. A failing seed, reduced,
  becomes a regression test.

These follow from ADR-0003 to ADR-0006 and the five above, so the plan
records them without ADRs:

- **The hub is a notesd with a listener.** `notesd --hub <addr>` serves
  the `/sync` endpoints there; `notesctl hub serve <vault>` makes a
  registered vault a hub vault, giving it a random sync ID and seeding its
  log with a create revision per file. A hub may keep vaults it does not
  serve. Its own writers (`notesctl` on it, other programs on its disk,
  and from M4 the web app and remote MCP) append revisions as pushes do.
- **The hub merges with M1's write path.** A push is a write into the
  hub's vault whose base is the base revision's hash: the same
  compare-and-merge (`merge.Note` for notes, `merge.Text` for other text),
  the same compare of the disk before the rename, and the same conflict
  version, now also a conflict revision. The hub looks a base up in the
  log as well as in its local versions, since the log keeps content
  longer. One merge path serves local writers and devices, and M1's
  writer-pair and `kill -9` tests already cover it.
- **A device applies, never merges.** M1's write path merges whenever the
  base is behind, which for a pulled revision would be a merge on a device
  ([ADR-0005](../adr/0005-sync-through-a-hub-with-revisions-and-three-way-merges.md)
  forbids it). `vault.Apply` writes a pulled revision only if the file
  still has its agreed hash and path, compared again just before the
  rename; otherwise it reports the change, and the sync loop pushes it
  first and applies the hub's answer. It streams content from `blobs/` at
  any size (the note API stops at 10 MB), passes every pulled path through
  the path guard, so a hub cannot write outside the vault, records `sync`
  versions with the revision's author, and removes a folder that a pulled
  delete or move leaves empty.
- **Pending changes are state, not a queue.** A device knows what to push
  by comparing its index (`files`) with its agreed state (`sync_files`): a
  file without an agreed row is a create, a moved or changed one a move or
  a put, an agreed row without a file a delete. A crash, an outage or a
  restart loses nothing to push, and there is no queue to replay or
  corrupt.
- **Pushes are idempotent.** Each push carries an ID the device never
  reuses; the hub records it with the revision and answers a repeat with
  the first answer, so a push whose answer was lost is retried safely.
  Every answer names the file's head after the push, which the device
  applies at once.
- **Pushes wait for quiet.** A device pushes a changed file after 2 s
  without another change to it, and at most 30 s after its first unpushed
  change, so typing makes a revision every few seconds rather than one a
  keystroke, and a long session still syncs.
- **Pulls bring heads.** A pull returns, for each file whose head is newer
  than the cursor, that head, in sequence order. Earlier revisions are
  history (`notesctl history`), not something a device replays, so a
  device that was away for a year needs no pruned content.
- **Files over 10 MB do not merge,** like files that are not text: the
  later push wins, and the other stays in the log with the file flagged.
  The API does not read them (M1), and a merge would hold three copies in
  memory.
- **Join matches by history.** When a device joins with files already in
  its folder, a file whose hash is a revision of the hub's file at the
  same path takes that revision as its agreed base, so an unchanged older
  copy simply takes the head. Only content the hub has never had at that
  path is pushed, as a create, and merged as one where the path exists.
  `notesctl sync reset` drops the state and joins again.
- **Events reach only the callers their domain admits.** The hub
  announces new revisions with a `log` event on a device's connection;
  `note` and `vault` events stay with local callers. The event fan-out
  takes the router's rule
  ([rpc-protocol](../specs/rpc-protocol.md#caller-kinds)).
- **Migrations become append-only with M2.** Sync's tables are
  `0002_sync.sql`, and `0001_init.sql` is frozen from then on: the 7-day
  trial's sync state must survive the fixes made during it.
- **Device tokens live in the Secret Service** through a port of
  frostmail's `internal/secrets` (frostmail ADR-0011), made by the planner
  since it brings the godbus dependency, which cards never add;
  `FROSTNOTES_SECRETS=file` keeps them in a private file for CI and the nsl
  machine ([overview](../design/overview.md#operational-notes)).
- **Golden merge cases stay with the planner.** The roadmap listed them as
  executor work, but an expected merge is a merge rule, and the merge
  library is the planner's (ADR-0010). `specs/merge.md` holds the rules
  and the cases; the executor writes simulation scenarios instead.

- **Done when:** a hub and two devices in one test process sync a
  generated 666-note vault both ways, each test above passes, and `make
  vault-it` passes with sync's kill points.
- **Result (2026-10-17): done.** `internal/hub` serves pairing (pending
  pairings in memory, approval only over the local socket, a token handed
  out once and kept as its SHA-256), the token check, the `/sync`
  WebSocket as caller `device`, blobs through `internal/blobxfer`, and the
  `log` and `hub` domains. A push is a write through the vault's actor:
  `vault.Push` applies the protocol's push rules over M1's write path and
  new primitives that stream from the blob store, and every change to a
  served vault appends its revision in the same `Tx` as its version
  (`vault.logRevision`). `internal/syncer` (not `internal/sync`, which
  would shadow the standard library's) pairs, joins by matching history,
  and runs a loop per vault that pushes what differs from the agreed
  state after its quiet period, applies the hub's answers, and pulls and
  applies heads with `vault.Apply`, which compares instead of merging.
  notesd gains `-hub` and `-hub-max-blob`; the daily prune thins a hub's
  log and keeps an unnamed blob a day.

  Tests, with a hub and two devices in one process, each cut off and
  healed through `syncer.Config.Dial`: two editors on one base, an outside
  edit and a pull, an agent's append and an edit, a delete against an edit
  and a move against an edit in both orders, two daily notes from one
  template, two moves onto one path, a case-only collision, revocation, a
  hub naming a path outside the vault, verify and history, and a generated
  666-note vault both ways in 3 s (150 notes under the race detector,
  where the hub's fsynced creates of 666 take over a minute). The hub's
  own tests pair over HTTP, check tokens and origins, revoke a live
  connection and repeat a push. `make vault-it` passes 100 kills in each
  of four modes, the two new ones a hub applying pushes (the log then
  agrees with the files) and a device applying heads (every agreed state
  names a version its file held): 175 s. The kill points inside a
  device's push (between an upload and its push, after the hub's commit
  and before its answer) need a hub and a device in one child, which is
  the simulation's harness: they move to Phase 5.

  The tests found three bugs, each fixed: the hub refused a stale delete
  without the head the device needs to restore the file; a device woke
  once per announcement rather than pulling once for all waiting; and
  `x/net/websocket`'s client always sends an `Origin`, so devices send
  `notesd://device`, which no browser can, and the hub refuses any other
  (the spec says so). `LogFile` gains the head's author and device, so an
  applied version says who made it. Mutations: a hub that overwrites
  instead of merging fails three cross-device tests; a device whose
  `Apply` skips its comparison fails only the vault's own test, since the
  loop checks the index first and the cross-device tests rescan before
  pulling, so the window `Apply`'s comparison guards (an outside edit no
  scan has seen) is the simulation's to reach.

  Latency (`TestISyncLatency`, an integration test): an edit reaches
  another device through a hub on loopback 2.007 s later, the 2 s quiet
  period and 7 ms of sync.

## Phase 5 — Simulation (planner)

- `internal/synctest` per
  [ADR-0020](../adr/0020-test-sync-with-a-seeded-simulation-of-a-hub-and-devices.md):
  the harness (a hub and N devices over loopback, through a transport that
  partitions, delays and drops answers), the seeded scheduler, the token
  oracle, the checks at each quiet point, the reducer for failing seeds,
  and regression seeds under `testdata/`.
- `make sync-sim` runs 10,000 steps over a hub and three devices,
  stepwise and concurrent; `make test` runs a few hundred steps on fixed
  seeds.
- Mutations, each run once and recorded here: a hub that overwrites
  instead of merging, a device that applies a pull without comparing, and
  a hub that drops conflict revisions must each fail the simulation.
- **Done when:** `make sync-sim` passes on 10 seeds in each mode, and each
  mutation fails it.

  **Result (2026-10-17): done.** `make sync-sim` passed 10 seeds of 10,000
  steps in each mode. A stepwise seed takes 9 to 10 minutes, writes
  about 7,000 tokens and ends with about 8,800 revisions over 700 to 770
  files; a concurrent seed takes about 90 s for the same tokens, and ends
  with about 2,000 files, since its outside edits and attachments make
  new files. The two regression plans pass too. The kill points Phase 4
  left here are the simulation's crash steps: a device after an upload
  and after the hub's answer, the hub after a push's rename, and an
  answer lost with its connection. `make vault-it` still passes 100 kills
  in each of its four modes. Each world first checks that every notesd's
  watcher sees its vault, since many notesd at once can use up
  `fs.inotify.max_user_instances`, and a vault without a watcher waits
  for rescans; runs on this machine go one per mode for that reason.

  The simulation found five sync bugs, each fixed with a test:
  - A create whose answer was lost, its file then moved, went out again
    as a second create, and the hub held two files for one; the device
    then stopped on its agreed state. No new change of a file is pushed
    now until the answer to its last push is applied
    (`TestALostAnswerAndAMoveMakeOneFile`, and a regression plan).
  - A create the hub merged, whose file moved while the push was in
    flight, had no agreed state and went out as a second create. The
    merge now applies where the file is
    (`TestAMergedCreateThatMovedMakesOneFile`).
  - A pull skipped, for good, a new file whose path a copy of another
    file still held, that file's move coming later in the pull. Such a
    head now waits, and the pull pages on with the cursor held below it
    (`TestANewFileWaitsForTheOneLeavingItsPath`, and a regression plan).
  - After a reset that raced an answer, `log.match` agreed a copy at a
    revision its path never had, and the device kept the old path with
    nothing pending. The match is now the file's revision at the copy's
    path, with that revision's hash, `revisionHash`, an addition to the
    protocol (`TestMatch`). An agreed hash that was not its revision's
    also made the hub refuse that file's conflict items on their base,
    the likeliest cause of one concurrent loss (seed 8, a stale edit's
    lost hunk after a reset).
  - `sync.status` left out local conflict versions not yet pushed.

  And the harness's own bugs: the oracle missed the line a crashed write
  took out, and a delete that read the disk before a pull landed; a
  quiet point did not wait for an outside edit the watcher had not yet
  indexed. One concurrent loss stayed unexplained: once in about 120
  seeds of 400 steps, a stale edit's token disappeared after a disk move
  of the same note on the same device (seed 4); it did not recur in
  1,000 later runs of seeds 4 and 8 of 200 steps, nor in the 10,000-step
  runs. Concurrent runs edit on disk only files they create, since
  another program's edit racing a pull's rename loses whichever renames
  first ([design/sync.md](../design/sync.md#testing)).

  Mutations, each run on 3 seeds of 400 steps per mode: a hub that
  overwrites instead of merging fails every seed in both modes, tokens
  lost by step 24 stepwise and step 99 concurrently; a device that
  applies a pull without comparing fails every concurrent seed and one
  stepwise seed, since a device that goes quiet after each step has
  usually pushed before it pulls; a hub that drops conflict revisions
  fails every seed in both modes.

## Phase 7 — Review and exit evidence

- An independent review of the hub's device endpoints and of the device
  loop: pairing abuse, token storage and comparison, the path guard on
  pushed and pulled paths, request and blob size limits, blob reads
  limited to logged content, revocation. Each finding is fixed with a
  test.
- **Done when**, each shown by a test or a recorded run:
  1. 10,000 seeded simulation steps over a hub and three devices converge
     with no lost token and no conflict file (`make sync-sim`).
  2. A 100 MB attachment syncs from one device to another through a hub,
     three notesd processes on loopback, arriving with its hash, and no
     process's peak memory grows more than 64 MB above its idle.
  3. The user's vault syncs between two machines and a hub for 7 days
     with zero lost edits: `notesctl sync verify` passes on each machine
     every day (its files equal the hub's heads, every push it made is in
     the hub's log, and each conflict is listed), and the user finds no
     edit missing.
- `make m2-evidence` records evidence 1 and 2. Evidence 3 is the user's to
  run, on real notes, once the open questions below are answered.

  **Result (2026-10-17): evidence 1 and 2 recorded; evidence 3 waits on
  the user.** An independent reviewer (a separate agent, read-only, with
  scratch tests in a copy of the repository) checked the scope above.
  Its findings, each fixed with a test:
  - *High:* a device keyed hubs by the ID a hub's answers claim, which
    anyone can learn, so a hub the user was led to pair with could take
    another hub's token and URL and draw that hub's vaults to itself.
    `sync.paired` now refuses a hub claiming the ID of one this device
    syncs vaults with at another URL (`TestAHubClaimingAnotherHubsIDIsRefused`).
  - A connection whose token passed its check as its device was revoked
    outlived the revocation. The hub checks the device again once it
    counts the connection, and caps a device at 64 connections
    (`TestARevocationWhileADeviceConnectsClosesIt`).
  - A name a file system cannot hold failed a whole push on the hub, and
    wedged a device's sync when pulled. The path guard now limits names
    to 255 bytes and paths to 4,000; sync's own names (numbers, parking)
    fit within them; the hub refuses only that item; a device skips such
    a head (`TestANameTheHubCannotHoldRefusesOnlyItsItem`,
    `TestCheckPath`, `TestBesideKeepsANameWithinTheLimit`).
  - An answer moving a file to a path the device ignores wedged its
    sync. It is recorded as the device's own refusal, and the file leaves
    its care with its edit merged on the hub
    (`TestAnAnswerAtAPathThisDeviceIgnores`).
  - *Low:* the hub's blob store, shared by every vault on its notesd,
    answered for all of them: `log.missing` and an upload's 204 told a
    device what the hub held, and a push could name such content to read
    it. Presence is now the vault's log or the device's own uploads; an
    upload is read and checked whatever the hub holds; a `missing`
    refusal stays pending until the device uploads again
    (`TestContentTheHubHoldsForAnotherVaultIsNotADevicesToName`).
  - *Low:* a device downloaded without a limit, so a hub could fill its
    disk; it stops past 1 GiB (`TestDownloadStopsAtTheDevicesLimit`).
  - *Notes, kept and written down:* the 8 pending pairings are the hub's,
    not a caller's, so anyone reaching the hub can delay a pairing; and a
    hub serves one person's devices, each of which may join every vault
    it serves ([design/sync.md](../design/sync.md#operational-notes)).

  The reviewer found sound: the constant-time pairing secret, the
  local-only approval, token storage and revocation's database side,
  caller isolation (a device reaches only the `log` domain and its

  symlinks, settings and case tricks, blob reads gated by logged content,

## Later / ideas

- Syncing `.frostnotes/` settings, once something writes them (M1's
  `vault.settings` idea).
- Resumable uploads, compression, and content-defined chunks for large
  attachments that change.
- Keeping recently seen devices' bases from pruning.
- A model of the protocol (TLA+, or a small model checker in Go), if the
  simulation finds races that stepwise runs cannot replay.
- Built-in TLS and browser sign-in: M4's authentication ADR.
- `vault.status` saying whether its watcher runs: without one (inotify
  instances used up) edits wait for a rescan, and only the log says so.

## Open questions

- *Answered 2026-10-17:* **the trial's hub and its TLS front.** An incus
  VM on the user's always-on server, behind that server's `tailscale serve`
  ([Phase 7](#phase-7--review-and-exit-evidence), the trial's machines).
- *Answered 2026-10-17:* **the trial's copies of the vault.** The hub's
  vault is the user's real vault on the SMB share, where Obsidian keeps
  working; the laptop and the device VM hold their own copies. The
  user has only ever opened the vault over SMB, with no Obsidian Sync.
- *Answered in Phase 4:* **sync latency.** An edit reaches another device
  2.007 s later on loopback, nearly all of it the quiet period. The target
  for M2 is 5 s over the trial's network at the default quiet period; M4's
  2 s from a phone needs a shorter quiet period for the web app's writes,
  which push on the hub directly anyway.
  *Measured 2026-10-25, on one clock* (lodge's notesd and the hub, both on
  the hub's VM): a web-app save reached the hub's log 2.08 s later at the
  median (min 2.05 s, p95 10.8 s, max 47 s; n=61), and an agent's write
  2.09 s (n=9), the 2 s quiet period included; a pull from the hub to that
  device took 0.03 to 0.14 s (n=5; 1 match that spans the initial pairing
  is left out). Across machines: UNKNOWN. The hub's VM and
  the device VM do not synchronize their clocks, and on 2026-10-25 they
  were 9.4 s and 17.0 s behind the laptop, whose clock is synchronized, so
  the logs' cross-machine times do not measure latency.
- **Retention's numbers**
  ([ADR-0019](../adr/0019-keep-every-revisions-record-and-thin-the-content-by-age.md))
  are a starting point: the trial measures the log's and the blob store's
  growth, and a new ADR changes them if needed. By the end of M2.
  *Measured 2026-10-25, after the trial:* the hub's `notesd.db` 6.7 MB and
  its blobs 6.1 MB (715 blobs), for an 8.1 MB vault; the laptop's blobs
  5.1 MB. No revision was pruned (763 of 763 kept). The trial gives no
  reason for a new ADR.
